# Web 文档检查系统分析

本文基于当前项目代码整理，主要涉及：

- 前端：`Frontend/frontend/src/App.vue`
- API：`web_api.py`
- Web 检查服务：`web_service.py`
- Excel 导出：`report/excel_writer.py`

## 1. 整体处理流程

```text
用户选择 .docx 文件
        │
        ▼
Vue 使用 FormData 发起 multipart/form-data 请求
        │
        ├── POST /api/check：上传并执行检查
        └── GET /api/check-progress/{progressId}：每 300 ms 查询进度
        │
        ▼
FastAPI 将上传文件保存到 output/web_jobs/<任务编号>/uploads/
        │
        ▼
Python 依次读取文档并执行各项检查规则
        │
        ▼
openpyxl 在后端生成总检查结果.xlsx
        │
        ▼
后端把 Excel Sheet 转为 JSON，同时返回 Excel 下载地址
        │
        ▼
Vue 将二维表格转换为 Markdown 进行预览
```

当前检查请求是一个持续到检查结束的长 HTTP 请求。进度查询是独立的短轮询请求，并不是 WebSocket 或 SSE。

## 2. 前端上传文件时使用什么请求格式？

前端使用浏览器原生 `FormData`，通过 `fetch` 发起 `POST /api/check` 请求：

```javascript
const formData = new FormData()
selectedFiles.forEach((file) => formData.append('files', file))

fetch('/api/check', {
  method: 'POST',
  headers: { 'X-Progress-ID': progressId },
  body: formData,
})
```

实际请求格式为：

```http
POST /api/check
Content-Type: multipart/form-data; boundary=...
X-Progress-ID: 32位十六进制字符串
```

每个文件使用相同的字段名 `files`，因此一次请求可以携带多个文档。`Content-Type` 不由代码手动填写，浏览器会自动生成正确的 boundary；如果手动设置，反而可能造成后端无法解析。

`X-Progress-ID` 由前端通过 `crypto.randomUUID()` 生成并去掉连字符，用于关联进度查询。它不是最终任务编号，也不用于下载报告。

## 3. Python 后端如何接收文件？

FastAPI 接口声明如下：

```python
async def check_documents(
    files: list[UploadFile] = File(...),
    x_progress_id: str | None = Header(default=None),
):
```

- `files` 接收 multipart 请求中所有名为 `files` 的文件。
- `UploadFile` 提供文件名和异步读取能力。
- 后端以 1 MB 为一块读取上传内容，并写入任务的 `uploads` 目录。
- 每个文件保存完毕后调用 `await upload.close()`。
- 文档检查属于同步、计算/文件解析工作，因此通过 `asyncio.to_thread()` 放到工作线程，避免检查期间完全阻塞 FastAPI 事件循环，使进度查询仍能响应。

后端目前只根据扩展名判断格式，没有验证 MIME 类型，也没有验证文件内容是否真的是合法 DOCX ZIP 包。

## 4. 文件存在哪里，什么时候删除？

### 4.1 任务目录

每次新检查先创建临时任务目录：

```text
output/web_jobs/<临时任务编号>/
├── uploads/
│   ├── 文档A.docx
│   └── 文档B.docx
├── metadata.json
└── 总检查结果.xlsx
```

成功的新任务会保留在该目录中，目前没有定时清理、过期时间或容量上限。

### 4.2 文档独立归档

每个成功检查的文档还会复制一份到：

```text
output/web_documents/<文件名哈希>/
├── 原始文档.docx
├── issues.json
└── metadata.json
```

这里的哈希只基于文件名（忽略大小写），不基于文件内容。同名文档再次检查时，会以暂存目录和备份目录的方式替换旧归档。

### 4.3 自动删除时机

| 场景 | 当前处理方式 |
| --- | --- |
| 上传、检查或导出失败 | 删除本次临时任务目录 |
| 同一文件名组合再次成功上传 | 新任务替换旧任务目录，旧备份被删除 |
| 发现相同组合的多个历史任务 | 保留本次沿用的任务编号，删除其他重复目录 |
| 同名文档独立归档更新 | 删除旧备份，只保留最新版 |
| 用户点击前端“清除结果” | 只清除页面状态和 `localStorage`，不删除后端文件 |
| 普通成功任务 | 长期保留，没有自动过期清理 |

因此，项目当前不适合在没有额外清理策略的情况下长期接收大量或敏感文档。

进度数据保存在 Python 进程内的 `CHECK_PROGRESS` 字典中，不写入磁盘。条目达到 200 个时，创建新进度会移除最早的一个条目；服务重启后全部消失。

## 5. 后端返回的数据结构是什么？

### 5.1 检查成功

`POST /api/check` 返回示例：

```json
{
  "jobId": "0123456789abcdef0123456789abcdef",
  "fileName": "总检查结果.xlsx",
  "documentCount": 2,
  "sheets": [
    {
      "name": "汇总",
      "rows": [
        ["序号", "文档名称", "问题总数"],
        ["1", "文档A.docx", "3"]
      ]
    },
    {
      "name": "文档A",
      "rows": [
        ["序号", "问题类型", "所在章节", "位置", "内容", "问题说明"]
      ]
    }
  ],
  "excelDownloadUrl": "/api/jobs/0123456789abcdef0123456789abcdef/excel",
  "replacedExistingTask": false
}
```

`rows` 中的单元格会统一转换为字符串，空单元格转换为空字符串。

### 5.2 恢复历史结果

`GET /api/jobs/{jobId}` 返回：

```json
{
  "jobId": "...",
  "fileName": "总检查结果.xlsx",
  "sheets": [],
  "excelDownloadUrl": "/api/jobs/.../excel"
}
```

这个接口不返回 `documentCount` 和 `replacedExistingTask`。

### 5.3 查询检查进度

`GET /api/check-progress/{progressId}` 返回：

```json
{
  "percent": 60,
  "message": "正在检查重复内容：文档A.docx",
  "currentFile": "文档A.docx"
}
```

前端每 300 ms 查询一次，主请求结束后停止轮询。

### 5.4 失败响应

FastAPI 错误通常为：

```json
{
  "detail": "具体错误信息"
}
```

主要状态码包括：

- `400`：没有文件或扩展名不正确。
- `413`：单个文件超过 50 MB。
- `404`：任务、报告或进度不存在。
- `422`：multipart 字段缺失或请求结构不符合 FastAPI 参数要求。
- `500`：文档解析、检查、Excel 生成或文件操作发生未处理异常。

## 6. 多个文档如何区分结果？

后端使用保存后的文件名作为 `all_file_issues` 字典的键：

```python
{
    "文档A.docx": [问题列表],
    "文档B.docx": [问题列表]
}
```

Excel 中：

- 第一个 Sheet 为“汇总”，每行记录一个文档及其各类问题数量。
- 后续每个文档对应一个明细 Sheet。
- Sheet 名来源于不含扩展名的文件名。
- Excel Sheet 名会过滤非法字符、截断到 31 个字符，并通过 `_1`、`_2` 等后缀避免重名。

同一批次内如果上传两个同名文件，保存时第二个会自动改为 `文件名_2.docx`，因此结果仍能区分。需要注意，返回结果和 Excel 中显示的是保存后的名称，而任务的 `metadata.json` 中记录的是原始上传名称。

## 7. 检查失败时前端如何显示错误？

前端在开始检查前会清空旧错误。收到响应后先解析 JSON：

```javascript
if (!response.ok) throw new Error(data.detail || '检查请求失败')
```

发生错误时会：

1. 清空当前 Sheet、选中 Sheet、报告文件名和 Excel 下载地址。
2. 将错误文本写入 `errorMessage`。
3. 在上传区域下方以红色文字显示错误。
4. 停止进度轮询并隐藏加载状态。

如果错误信息包含 `fetch`，前端会显示：

```text
无法连接 Python 检查服务，请确认后端已启动。
```

否则直接显示后端返回的 `detail`。恢复上次结果失败时，404 会提示结果已不存在；其他错误统一提示检查 Python 服务是否启动。

当前不足是前端假定所有响应都能调用 `response.json()`。如果代理或服务器返回 HTML/纯文本错误页，JSON 解析错误可能掩盖真正原因。另外，用错误字符串是否包含 `fetch` 判断网络错误不够稳定。

## 8. Excel 报告由前端还是后端生成？

Excel 由 Python 后端生成。

处理链路为：

1. `web_service.py` 汇总每个文档的问题。
2. `report/excel_writer.py` 使用 `openpyxl` 创建 `总检查结果.xlsx`。
3. 后端再使用 `openpyxl` 读取该 Excel，将每个 Sheet 转为二维数组放进 JSON。
4. 前端将二维数组转换为 Markdown，仅负责页面预览和 Markdown 下载。
5. 用户点击“下载检查结果 Excel”时，前端访问后端的 `/api/jobs/{jobId}/excel` 下载已生成的文件。

前端不生成也不修改 Excel。

## 9. 文件过大、格式错误和重复上传如何处理？

### 9.1 文件过大

- 限制为单个文件最大 50 MB。
- 后端按 1 MB 分块读取并累计大小。
- 超过限制时返回 HTTP `413`。
- 本次任务目录会被删除，包括此前已经保存的同批文件。
- 当前没有限制一次上传的文件数量和总大小。
- 由于限制在接收并写盘过程中执行，超大请求仍会先经过 Web 服务器/multipart 解析的一部分流程。

### 9.2 格式错误

- 前端文件选择框使用 `accept=".docx"`，这是浏览器选择提示，不是安全校验。
- 后端再次检查文件名扩展名是否为 `.docx`，忽略大小写。
- 只要一份文件扩展名错误，整批请求返回 HTTP `400`，不会开始检查。
- 伪装成 `.docx` 的损坏文件会在 Python 解析阶段失败，最终返回 HTTP `500`。

### 9.3 重复上传

重复任务的判断依据是“文件名组合”：

- 忽略文件选择顺序。
- 忽略文件名大小写。
- 不比较文件内容、文件大小、修改时间或内容哈希。

如果文件名组合与历史任务相同：

1. 先在新临时目录完成上传、检查和报告生成。
2. 全部成功后，用新目录替换旧任务目录。
3. 沿用旧 `jobId`。
4. 返回 `replacedExistingTask: true`。
5. 如果新检查失败，旧任务仍保留，可避免成功结果被半成品覆盖。

这意味着内容完全不同但文件名相同的文档也会被认定为同一任务的新版本；内容完全相同但文件名不同则会创建新任务。

## 10. 为什么选择 Vue 和 Python？

项目代码没有记录正式的技术选型决策，以下是结合当前实现得出的合理分析。

### Vue 的适配点

- 页面包含文件选择、加载状态、进度、Sheet 切换和 Markdown 预览，Vue 的响应式状态很适合这类交互。
- 当前界面规模较小，Vue 单文件组件可以集中管理模板、逻辑和样式，开发成本较低。
- Vite 提供启动快、配置少的本地开发环境，并通过代理把 `/api` 转发给 Python 服务。
- Markdown 预览可直接通过 `markdown-it` 集成。

### Python 的适配点

- 项目的核心工作是 DOCX 解析、文本规则检查和 Excel 导出，`python-docx`、`openpyxl` 等库成熟且直接。
- 检查规则以 Python 函数组织，便于快速增加正则和文档结构规则。
- FastAPI 能直接接收多文件上传、生成 JSON API，并自动处理参数校验。
- 命令行检查与 Web 检查可以复用同一套 parser、checker 和 report 模块。

这是一套适合本机工具和内部小规模使用的组合；如果要面向大量并发用户，需要补充任务队列、持久化状态、安全控制和部署设计。

## 11. 当前项目的不足

### 11.1 文件生命周期和隐私

- 成功文件会同时存在于任务目录和独立文档归档，形成两份原文副本。
- 没有自动过期、磁盘配额、后台清理任务或后端删除接口。
- 前端“清除结果”不会删除服务器文件，按钮名称容易让用户误解。
- 没有针对敏感文档的加密、脱敏或访问审计。

### 11.2 身份认证和接口安全

- API 没有登录、权限控制或任务所有权校验；知道 `jobId` 即可读取结果或下载 Excel。
- 文件类型只检查扩展名，没有 MIME、ZIP 结构和 DOCX 内容验证。
- 没有文件数量、请求总大小、请求频率和并发限制。
- HTTP 500 会把底层异常文本返回前端，可能暴露内部路径或实现信息。

### 11.3 重复任务识别不准确

- 任务去重只依据文件名组合，无法判断内容是否真的相同。
- 文档独立归档也只按文件名建立哈希，不同内容的同名文档会互相覆盖。
- 更稳妥的方式是结合内容 SHA-256、文件名和业务版本标识。

### 11.4 进度机制只适合单进程

- 进度保存在进程内字典，服务重启即丢失。
- 如果 Uvicorn 启动多个 worker，上传请求和进度查询可能落到不同进程，导致查询 404。
- 当前百分比按阶段权重估算，并非按真实段落数量或实际耗时计算。
- 300 ms 轮询频率较高，可考虑 SSE、WebSocket，或降低轮询频率。
- 已完成的进度不会立即删除，只在条目达到 200 个后逐步淘汰。

### 11.5 任务执行和并发

- 检查仍依附于一个长 HTTP 请求，没有独立任务队列、重试、取消和超时控制。
- 用户关闭页面或网络断开后，后端任务无法由用户取消。
- 多个请求同时替换相同文件组合或同名文档归档时没有锁，可能发生目录竞争。
- 查找重复任务需要扫描 `web_jobs` 目录；任务数量增长后性能会下降。

### 11.6 大结果性能

- 后端生成 Excel 后又完整读取一遍，并将所有 Sheet、所有单元格放入 JSON。
- 前端一次性把所有行转换成 Markdown 并渲染，大文档或问题很多时会占用较多内存并使页面变慢。
- 没有分页、按 Sheet 延迟加载、虚拟表格或结果条数上限。

### 11.7 错误处理和可观测性

- 错误响应没有稳定的业务错误码，前端主要依赖中文文本。
- 网络错误判断依赖错误信息是否包含 `fetch`，兼容性较弱。
- 非 JSON 错误响应没有回退解析。
- 没有结构化日志、任务耗时统计、失败阶段记录和运行指标。

### 11.8 工程化

- 当前未发现自动化测试目录，上传、重复替换、报告格式和检查规则缺少回归测试保护。
- 前端主要逻辑集中在单个 `App.vue`，继续增加功能后维护成本会提高。
- 缺少生产环境部署配置；当前 Vite 开发服务器和 `--reload` 方式只适合本地开发。
- 缺少数据库或任务索引，任务元数据依赖目录和 JSON 文件管理。

## 12. 建议的改进优先级

### 优先级 P0：数据安全和稳定性

1. 增加后端删除任务接口，并明确“仅清除页面”与“删除服务器文件”的区别。
2. 增加保留天数和定时清理策略，限制总磁盘占用。
3. 使用内容哈希识别重复文件，并验证 DOCX 文件结构。
4. 增加上传文件数量、总大小和并发限制。
5. 对外部署前增加身份认证和任务归属校验。

### 优先级 P1：任务系统

1. 将检查改为“创建任务后立即返回 jobId，后台执行，前端查询状态”。
2. 使用 SQLite/Redis 等保存任务状态和进度，支持重启恢复及多 worker。
3. 增加任务超时、取消、失败阶段和重试机制。
4. 对同一任务或同名归档增加并发锁。

### 优先级 P2：体验和工程质量

1. 结果按 Sheet 按需加载，问题明细支持分页。
2. 使用稳定错误码，并兼容 JSON 与纯文本错误响应。
3. 拆分前端上传、进度、结果预览组件。
4. 为检查规则、API、重复替换和 Excel 输出增加自动化测试。
5. 增加生产构建、静态文件托管及部署文档。

## 13. 相关 API 汇总

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/health` | 后端健康检查 |
| `POST` | `/api/check` | 上传一个或多个 DOCX 并同步等待检查完成 |
| `GET` | `/api/check-progress/{progressId}` | 查询当前检查进度 |
| `GET` | `/api/jobs/{jobId}` | 恢复历史任务结果 |
| `GET` | `/api/jobs/{jobId}/excel` | 下载后端生成的 Excel 报告 |
